# Test a Go App with Keploy

Keploy is an open source testing tool that records the API calls your app
already handles and turns them into test cases. This tutorial walks through
the Gin + MongoDB URL shortener quickstart from the Keploy samples. At the
end you will have a replayable test suite for a real REST API without writing
any test code by hand.

<Callout type="info" title="How Keploy works">
When you run <code>keploy record</code>, it captures every incoming HTTP call
and every outgoing database call, and saves them to your repo as YAML files.
When you run <code>keploy test</code>, it replays those same calls and fakes
the database responses, then checks that your app behaves the same as it did
during recording.
</Callout>

## Why this matters for Go developers

Three common pain points of integration testing go away with Keploy:

| Pain | Traditional approach | With Keploy |
| --- | --- | --- |
| Writing mocks | Hand-stub every database call | Mocks are generated from real traffic |
| Keeping data clean | Seed scripts and teardown steps | The database is faked during tests, so nothing to clean |
| Test drift | Tests rot as the code changes | Re-record the suite in seconds |

The core idea: your API traffic is already a test suite. Keploy saves it
instead of losing it when your `curl` command finishes.

## Prerequisites

Before starting, make sure you have:

- **Go 1.20 or newer**. Check with `go version`.
- **Docker** running. We use it only for MongoDB.
- **Keploy CLI**. Install it if you do not have it yet:

```bash
curl --silent -O -L https://keploy.io/install.sh && source install.sh
keploy -v
```

<Callout type="note">
Tested on macOS (Apple Silicon) and Linux. On Windows, run everything inside
WSL2. Full install instructions are in the
[official installation guide](https://keploy.io/docs/server/installation/).
</Callout>

## Quickstart

Here is the whole flow in five commands:

```bash
# 1. clone the sample app
git clone https://github.com/keploy/samples-go.git && cd samples-go/gin-mongo

# 2. start MongoDB in Docker
docker run --rm -d -p 27017:27017 --name mongoDb mongo

# 3. record a test suite
sudo -E keploy record -c "go run main.go handler.go"

# 4. hit the API (in another terminal)
curl --request POST \
  --url http://localhost:8080/url \
  --header 'content-type: application/json' \
  --data '{"url": "https://google.com"}'

# 5. replay your test suite
sudo -E keploy test -c "go run main.go handler.go" --delay 10
```

The rest of this tutorial explains each step in detail.

## Step 1: Clone the sample app

We use the official **gin-mongo** sample from Keploy. It is a URL shortener:
you send a long URL and it returns a short one.

```bash
git clone https://github.com/keploy/samples-go.git
cd samples-go/gin-mongo
go mod download
```

Two files matter here:

<Steps>
<Step number={1} title="main.go">
  Connects to MongoDB on <code>localhost:27017</code>, sets up the Gin
  routes, and starts the server on port <code>8080</code>.
</Step>
<Step number={2} title="handler.go">
  <code>POST /url</code> shortens a URL. <code>GET /:shortUrl</code> redirects
  back to the original. Each handler calls MongoDB directly.
</Step>
</Steps>

That is the whole app.

## Step 2: Start MongoDB

The app needs a MongoDB instance. One container is enough:

```bash
docker run --rm -d -p 27017:27017 --name mongoDb mongo
```

Check that it is running:

```bash
docker ps --filter name=mongoDb
```

## Step 3: Record your test suite

Tell Keploy to run your app and watch everything that happens:

```bash
sudo -E keploy record -c "go run main.go handler.go"
```

You will see the Keploy banner, then your app's startup logs. Keep this
terminal open while you test the API.

### Send your first request

In a new terminal:

```bash
curl --request POST \
  --url http://localhost:8080/url \
  --header 'content-type: application/json' \
  --data '{"url": "https://google.com"}'
```

You get a response like this:

```json
{
  "ts": 1645540022,
  "url": "http://localhost:8080/Lhr4BWAi"
}
```

Two things happened at the same time:

1. Your request hit the app and was served normally.
2. Keploy copied that request and response pair into a **test case**, and
   copied the MongoDB call the handler made into a **data mock**.

### Send a second request

Capture one more call so the suite has more than one test:

```bash
curl --request GET \
  --url http://localhost:8080/Lhr4BWAi
```

This redirects you back to `https://google.com`.

<Callout type="tip" title="Save the short URL">
The short code <code>Lhr4BWAi</code> is random. Save the one you actually
got. You need it in Step 5 to check that the redirect replays correctly.
</Callout>

## Step 4: Understand what got recorded

Stop the recording with `Ctrl+C` and look at what appeared in your project:

```
gin-mongo/
├── keploy/
│   ├── test-1.yml             the POST /url request and response
│   ├── test-2.yml             the GET /Lhr4BWAi request and response
│   ├── mocks/
│   │   └── mocks-1.yml        the MongoDB calls in wire protocol detail
│   ├── reports/
│   │   └── test-run-...json   the outcome of the last keploy test run
│   └── suite-*.yaml
```

Open `test-1.yml`. This entire file is a test you did not write:

```yaml
version: api.keploy.io/v1beta2
kind: Http
name: test-1
spec:
  metadata: {}
  req:
    method: POST
    proto_major: 1
    proto_minor: 1
    url: http://localhost:8080/url
    header:
      Accept: "*/*"
      Content-Length: "33"
      Content-Type: application/json
      Host: localhost:8080
      User-Agent: curl/7.77.0
    body: |-
      {
        "url": "https://google.com"
      }
    body_type: ""
  resp:
    status_code: 200
    header:
      Content-Length: "65"
      Content-Type: application/json; charset=utf-8
      Date: Sun, 01 Oct 2023 15:15:47 GMT
    body: '{"ts":1696173347979970488,"url":"http://localhost:8080/Lhr4BWAi"}'
    body_type: ""
    status_message: ""
    proto_major: 0
    proto_minor: 0
  objects: []
  assertions:
    noise:
      - header.Date
  created: 1696173352
```

Look at the `assertions.noise` block. Keploy added `header.Date` on its own,
because HTTP responses contain headers that differ between runs. Anything
listed under `noise` is ignored during comparison.

<Callout type="aha" title="A test you never wrote">
This YAML is a complete test case, and you will never edit it by hand except
for the <code>noise</code> list. Everything else is diffed and reported
automatically.
</Callout>

Now open `mocks/mocks-1.yml`. This file records every MongoDB query your
handler made, using MongoDB's own wire protocol.

<Callout type="tip" title="Mocks replace the database">
The mocks are why you do not need a live MongoDB during tests. Step 5 runs
the whole suite with MongoDB turned off on purpose.
</Callout>

## Step 5: Replay your tests

Stop any running processes, including the recorder and MongoDB if you like,
then run:

```bash
sudo -E keploy test -c "go run main.go handler.go" --delay 10
```

Keploy starts your app and replays each test case:

- It sends the recorded request to your server.
- For each MongoDB call the handler makes, it answers with the recorded mock
  instead of the real database.
- It compares the response your app produces now against the recorded
  response, ignoring the noise fields.

Expected output, all green:

```
running tests...
    1. test-1 (OK)       ✓
    2. test-2 (OK)       ✓
total tests: 2, passed: 2, failed: 0
```

### If a test fails

The most common first-run failure is `body.ts`. The URL shortener puts a
timestamp in every response, and that value changes on every run, so Keploy
reports a diff. Fix it by adding it to the noise list:

```yaml
# edit keploy/test-1.yml, near the bottom
assertions:
  noise:
    - header.Date
    - body.ts
```

Run `keploy test` again and everything passes.

<Callout type="warning" title="The --delay flag">
`--delay 10` gives your app 10 seconds to start before Keploy replays tests.
On a slow machine or a cold start, increase this. If tests fail with a
connection refused error, this is usually the reason.
</Callout>

## Step 6: See Keploy catch a regression

Change your app on purpose and see whether Keploy notices.

Open `handler.go` and change what a handler returns: a status code, a field,
anything. Then run:

```bash
sudo -E keploy test -c "go run main.go handler.go" --delay 10
```

Keploy reports exactly which test failed and which field changed:

```
running tests...
    1. test-1 (FAIL)    ✗  response body differs
    2. test-2 (OK)      ✓
total tests: 2, passed: 1, failed: 1
```

Delete the YAML files and record again when you want the behavior to change.
This becomes your normal workflow:

| Change | What to do |
| --- | --- |
| Refactor internals | Run `keploy test`. It should still pass. |
| Change API behavior | Run `keploy record` again, then replay. |

## Common problems and fixes

<Callout type="warning" title="MongoDB must be up before recording">
If <code>keploy record</code> starts your app but it dies immediately with
<code>server selection error</code>, the MongoDB container is not running:

```bash
docker ps --filter name=mongoDb
docker start mongoDb
```
</Callout>

<Callout type="warning" title="Port already in use">
If you see <code>address localhost:8080 already in use</code>, another
process holds the port. Find and stop it:

```bash
lsof -i :8080
kill -9 <PID>
```
</Callout>

<Callout type="warning" title="Go version mismatch">
If <code>go mod download</code> fails with a version error, update your local
Go installation. The sample targets a recent toolchain.
</Callout>

<Callout type="tip" title="Commit the keploy directory">
The <code>keploy/</code> directory is plain YAML that diffs cleanly in code
review. Once the team trusts the suite, adding a <code>keploy test</code>
step to CI is a reasonable next move.
</Callout>

## What Keploy is not

To set expectations correctly:

- It is not a unit test replacement. Keploy covers integration behavior, not
  individual function logic.
- It does not handle true randomness. Responses with genuinely random values,
  such as a live payment API, need careful `noise` configuration.
- It is not a load testing or fuzzing tool. It is a capture and replay
  harness.
